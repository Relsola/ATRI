## 1. 范围与规范约定

本文定义语言对使用者可见的词法、语法、类型和执行行为，包括编译期执行、模块与外部函数互操作。编译器的实现语言、AST 内部结构、IR 设计、优化算法、汇编器和链接器选择由架构文档规定。

本文从原设计草案抽离，不将推荐方案自动升级为已确定规则。用户已授权先拟定基础默认行为再审查；新增候选集中在[基础默认行为与设计取舍：审查稿 v0.1](language_defaults_review_v0_1.md)，本规范仍是统一入口。

审查稿为数值、初始化、内存、字符/字符串、控制流和模块等提供完整的一组候选默认行为，每项包含理由和重大替代方案。本文的待定项已有提案时，仍待用户审查；不得将候选方案当成已确认规则。用户已确定规则优先，审查后再将相应条款合入本规范正文。

### 1.1 规则状态

| 标记 | 含义 |
| --- | --- |
| **已确定** | 原草案已明确或用户在后续讨论中已确认的规则；细节仍可能由待定项补齐 |
| **建议** | 原草案推荐方案，或明确标注的新增讨论建议；尚未冻结 |
| **默认提案／待审查** | 用户授权先拟定的具体默认行为；详见审查稿 BD 编号，尚未视为用户确认 |
| **待定** | 尚无足够规则，必须决策后才能作为实现与一致性测试依据 |
| **示意** | 用来说明意图的代码或语法片段，不是完整形式语法 |

“必须”“不得”在**已确定**规则中表示规范要求；在**建议**部分只描述该建议被采纳后的要求。示例不隐含未写明的语言规则。

待定项不等于“实现可以任意选择”。若某个实现子集涉及待定项，应先确定相应规则，或者明确说明该能力尚不支持。

### 1.2 版本与变更

本文的 v0.1 是文档版本，不表示存在一个已经完整定义、实现和冻结的语言版本。

后续修改应记录规则状态的变化。语义变更应同步更新对应示例和测试；冻结版本应明确实现范围及仍然排除的能力。

## 2. 语言模型与实现范围

### 2.1 基本模型

**已确定：**

- 语言为强类型、命令式、偏底层的通用编程语言。
- 核心定位为面向数据编程（DOP），优先服务显式数据表示、布局控制和批量处理，以此指导语言与基础库设计。
- 采用类 C 语法，优先保证语义明确和可解析性。
- 区分运行期执行和由 `run` 显式要求的编译期执行。
- 顶层声明顺序无关，不要求使用者编写前向声明。
- 正式方向包含完整目标平台 C ABI 兼容，以及能够访问、构造和修改任意 AST 的编译期元编程。
- 运行时遵循零开销设计方向；对等价手写底层代码的成本定义、原始指针访问与内置数组检查的区别及必要语义成本的边界，见默认提案 BD-00/15。
- 语言不提供异常机制，不引入 throw/catch 或语言异常栈展开。编译诊断、普通错误返回以及目标硬件/客户机异常按各自契约处理。

**建议：**首版采用手动内存管理和显式错误处理，不引入所有权检查、借用检查或强制 GC；不提供语言异常已由用户明确确认。

### 2.2 平台与阶段

首个实现目标是 Windows x86-64，首版按 Hosted 环境设计。Freestanding 和其他目标平台属于后续扩展。

语言的完整目标能力与首次自举所需的实现子集应分别记录。能够自举只说明实现足以编译编译器自身，不自动说明已实现本规范的全部能力。

核心可自举子集尚未冻结，候选范围见附录 A。原路线中的 M0 至 M5 是工程里程碑，不是独立的语言版本。

### 2.3 DOP 定位对当前设计的影响

**已确定的方向：**面向数据是语言核心定位，不以 OOP 对象体系作为设计中心。现有结构体、数组、显式指针、模块函数与零开销方向继续沿用，不据此推翻前后端架构。

**设计影响与后续建议：**

- 保持结构体表示与内存成本可见，按已接受的 BD-16 保留声明顺序布局，不为“面向数据”自动重排可观察字段或改变 C 布局。
- 以普通数据结构和批量处理函数组织接口，组合与索引/句柄可作为后续基础库设计手段；不隐式引入对象头、继承关系或虚调用。
- 数组的完整类型/值语义与基础容器接口继续优先审查。数据访问模式可以选择数组内嵌结构体（AoS）或将字段分别放入数组（SoA），两者的适用性由算法与测量判断。
- 数据组织与算法实现相对独立，编译期代码生成可在以后帮助构造批量接口；不要求第一轮先实现 SIMD、自动向量化或专用 SoA 语法。
- 不从 DOP 一词额外推导“所有数据不可变”“禁止封装/方法语法”或“所有数据都必须改成 SoA”；这些若有需求仍需单独审查。

以下只示意数据组织，不新增数组或方法规则：

```text
struct Position {
    x: f32;
    y: f32;
}
positions: [1024]Position; // AoS：每个元素包含 x/y

struct PositionColumns {
    x: [1024]f32;
    y: [1024]f32;
}                            // SoA：分别保存 x 列和 y 列
```

AST、链表和其他图状数据仍可按真实访问需求使用指针或索引。DOP 是设计取向，不承诺仅改变语法就提高缓存效率或性能。

## 4. 语法框架

### 4.1 已确定的形式

```text
fn add(a: i32, b: i32) -> i32 {
    return a + b;
}

a: i32 = 10;
b: i32 := 20;
c: u8 = cast<u8>a;
```

- 函数形式为 `fn name(parameters) -> ReturnType`。
- 参数、局部绑定及命名字段统一采用 `name: Type`，名称与类型通过冒号分隔；不再采用 `Type name`。函数返回类型仍放在 `->` 后。
- 普通变量写作 `name: Type [= expression];`，编译期常量写作 `name: Type := expression;`；不使用 `let` 或 `const` 声明关键字。
- 普通类型之间的转换显式书写为 `cast<T>expression`。

### 4.2 不完整的 EBNF 片段（示意）

本节仅整理草案已有的声明形状，不作为完整 Parser 的验收依据。引号内为终结符，`[ ]` 为可选项，`{ }` 为重复项；未展开的非终结符尚待定义。

```ebnf
function-definition = "fn", identifier, "(", [parameter-list], ")",
                      "->", type-expression, block ;
parameter-list      = parameter, { ",", parameter } ;
parameter           = identifier, ":", type-expression ;
binding-declaration = variable-declaration | constant-declaration ;
variable-declaration = identifier, ":", type-expression,
                      ["=", expression], ";" ;
constant-declaration = identifier, ":", type-expression,
                       ":=", expression, ";" ;
```

普通变量省略初始化表达式时执行默认零初始化；编译期常量必须显式提供可在编译期求值的初始化表达式。各类型零值的定义见第 6.1、10 节，初始化器表达式的完整语法仍待补齐。

**名称空间边界：**`::` 继续表示模块限定访问，例如 `math::add(1, 2)`；不将 `name :: expression` 同时定义成常量声明，避免它与函数体内的限定调用产生二义性。类型推导的常量/变量写法均待定，不靠空格区分语义。当前 `:=` 是完整的双字符符号，不能拆成 `: =`。

### 4.3 待补齐的语法

- 完整的顶层声明、局部声明与语句产生式。
- 类型表达式，尤其是函数类型、指针、数组的组合。
- 运算符优先级、结合性、赋值和复合赋值。
- `cast<T>` 后操作数的结合范围，以及 `<`、`>` 的解析边界。
- `for` 初始化/迭代项的完整语法、尾逗号和空语句等规则；C 形状 for 及首版无标签控制流已由 BD-19 确认。
- 结构体 `{.field = expression}` 初始化器的完整语法、其他聚合值构造、字段访问、枚举变体构造和模式解构。
- `run` 表达式、代码块及其允许出现的位置。
- 属性、模块可见性和程序入口的具体语法。

### 4.4 当前已实现的基础编译子集

Stage 0 已实现 `name: Type` 参数/普通变量、`name: Type := expression` 编译期常量、整数/布尔表达式与直接函数调用，包含 i32/i64/bool/*i32 的名称/类型检查、前向函数引用、编译期分支/循环/递归、多基本块 CFG、局部对象 load/store、直线代码传播/折叠/内联及 Windows x64 汇编输出。BD-19 的条件、循环、break/continue 已实现，控制体强制使用花括号。

完整实现范围见[基础编译原型](parser_subset_v0_1.md)及[整数指针子集](pointer_subset_v0_1.md)，内部契约见 [IR 设计](ir_design_v0_1.md)。当前不实现浮点运算、defer/match、多层指针、指针转换/排序、聚合或编译期 AST API；原型限制和暂用的候选规则不自动冻结整门语言规范。

## 5. 类型系统

### 5.1 内置类型

**已确定的方向：**

| 类型 | 含义与边界 |
| --- | --- |
| `bool` | 布尔类型；表示布局和与整数的转换规则待定 |
| `char` | 用户确定采用的字符类型方向；位宽、编码、与整数的关系及字面量规则待定 |
| `i8/i16/i32/i64` | 对应位宽的有符号整数；表示和运算边界待定 |
| `u8/u16/u32/u64` | 对应位宽的无符号整数；运算边界待定 |
| `f32/f64` | 计划支持的浮点类型；精确格式、舍入和特殊值行为待定 |
| `void` | 计划支持；可出现的位置与是否存在值待定 |

不提供传统含义模糊的 `int` 类型。

**原草案建议：**`isize` 和 `usize` 分别为宽度与目标平台指针相关的有符号和无符号整数。首个目标上均为 64 位。

**修订讨论（2026-11-15，TYPE-03）：**用户提出当前可能不需要这两个类型。候选方案是首次实现暂不提供，以固定宽度整数表达所需计算；若采纳，应同步确定 `sizeof`、`alignof`、长度、索引及 C ABI 大小参数的类型。暂缓首版支持不等于永久排除平台相关整数类型。此项尚未冻结。

**当前首版建议（2026-11-16）：**首次 Windows x86-64 实现暂缓 `isize/usize`；`sizeof`、`alignof`、缓冲区长度/容量和分配大小采用 `u64`，需要负值的偏移或差值采用 `i64`。索引允许的整数类型、越界行为和精确 C ABI 映射仍待确定。该建议保留 TYPE-03 待确认状态，不将所有平台的大小类型永久固定为 64 位。

### 5.2 复合类型

语言方向包含指针、数组、函数类型、结构体、无标签联合体和枚举变体。

```text
*i32       // 指针示意
[16]u8     // 定长数组示意
```

函数类型与函数指针的拼写、类型等价性、递归类型的合法性、类型别名及限定规则待定。

### 5.3 类型值

**建议：**提供内置 `type` 或等价机制，允许编译期程序表示和操作类型。

**待定：**类型值能否存储、传递和比较，是否仅能存在于编译期，以及如何与 AST 反射配合。此项不表示已经确定泛型语法或完整泛型系统。

### 5.4 类型转换与字面量

**已确定：**禁止普通类型之间的隐式转换。显式转换采用 `cast<T>expression`。

**建议：**字面量可以依据目标上下文定型，但必须检查范围与合法性。字面量定型与已具有具体类型的普通值转换分开规定。

**待定：**无上下文字面量、负整数字面量、混合类型运算、分支公共类型，以及指针/数组是否存在特殊转换。

### 5.5 字符与字符串

**已确定的方向（2026-11-16）：**提供 `char` 表达字符，并采用字符指针表达低层字符串接口。用户使用 `char*` 描述字符指针；原草案指针拼写为 `*T`，因此字符指针的正式拼写保留待定，不在本轮自动改变整个指针语法。

**待定：**是否提供内置 `string`。字符指针本身并未确定长度、编码、结尾标记、所有权或可变性，因此不视为已经定义了完整的字符串值语义。

在字符/字符串规则冻结前，需要确定：

- `char` 表示一个字节、编码单元还是 Unicode 标量值，位宽与 `u8` 是否为同一类型。
- 字符和字符串字面量的拼写、编码、转义及字面量的精确类型。
- 字符指针字符串是否要求零结尾，长度按字节还是字符计算。
- 字符串字面量的存储期、可写性，以及指针与长度的获取方式。
- `string` 若加入，是借用视图还是拥有内存的容器；复制、分配与释放如何工作。
- 动态字符串功能是否先由基础库提供，C ABI 接口如何对接。

以上均为开放问题，不因采用字符指针而自动继承其他语言的字符串规则。

## 6. 声明、绑定与函数

### 6.1 绑定

**已确定：**

- 普通变量使用 `name: Type [= expression];`，允许重新赋值，省略初始化器时执行默认零初始化。
- 编译期常量使用 `name: Type := expression;`，必须在编译期成功得到结果，不允许重新赋值。
- 不再提供仅表示运行期不可变绑定的 `const` 声明，也不使用 `let` 引导普通变量。
- 常量初始化可以调用能够在编译期执行的函数；无法求值、非法运算或超出编译资源限制时必须诊断，不能退回运行期初始化。
- 常量合法性不取决于优化开关或内联启发式。当前原型不允许常量初始化直接读取普通局部变量或函数参数，即使优化器恰好能推导出其值；被编译期调用的函数仍可使用其已知实参和内部可变局部变量完成计算。

**优化与编译期求值：**编译器可以对普通变量进行已知值传播、折叠和函数内联，但这些是保持语义的优化。`:=` 则明确要求在编译期得到常量结果；`examples/constants.txt` 中的 `add(1, 2)` 在 -O0 下也必须成为常量 3。`run` 的长期目标仍包括更一般的编译期执行与 AST API，本轮整数常量求值不替代完整目标。

```text
a: i32;              // 默认初始化为 0
buffer: [16]u8;      // 所有元素默认初始化为 0
b: i32 := 20;
```

```text
missing: i32 :=;     // 编译错误：缺少初始化表达式
```

默认零初始化是语言层面的值规则；布局填充字节是否清零、动态分配的原始内存是否清零，不由这条绑定规则自动决定。布尔、指针、枚举和联合体的具体零值及合法性仍需定义；不能假设任意类型都具有合法的全零位表示。

编译期常量的值不可赋值；这不自动承诺其指针指向的对象始终不变。常量实体化、取地址、地址常量、聚合常量的可写访问及目标只读 API 仍待明确，不恢复此前的运行期 const/深度只读提案。

**待定：**各类零值的边界、局部与全局绑定的差异、全局初始化顺序、遮蔽、重复声明、可取地址性和生命周期。

### 6.2 函数

**已确定：**使用尾部返回类型，支持递归和跨文件调用；顶层函数不需要前向声明。

```text
fn add(a: i32, b: i32) -> i32 {
    return a + b;
}
```

函数指针是计划能力，具体类型和调用语法尚未完整定义。

**待定：**函数参数的值传递规则、聚合返回、缺少 `return`、`void` 返回形式、重载、默认参数、可变参数及入口函数约定。未明确列出的能力不视为默认支持。

### 6.3 名称解析

**已确定：**顶层声明顺序无关。

这不自动允许所有声明循环。例如递归函数、按值递归结构体、循环全局初始化和编译期依赖循环需要分别规定。

局部绑定是否必须先声明后使用、各名称空间是否分离，以及模块之间的可见性尚待确定。

## 7. 表达式与运算

### 7.1 求值与副作用

**已确定（2026-11-16）：**逻辑 `!`、`&&`、`||` 的操作数必须为 `bool`，结果为 `bool`。指针不具有逻辑操作专用的真值转换；判断指针非空应先显式比较，不能直接使用 `!pointer` 或 `pointer && condition`。

**待定：**左右操作数、函数参数、赋值两侧及聚合初始化项的求值顺序。

**建议：**明确规定顺序，避免编译期解释器、优化器和运行期后端产生不同的可观察行为。短路求值、不可到达表达式和副作用还需单独说明。

### 7.2 数值运算与比较

草案使用了加法、乘法等表达式，但尚未给出完整运算符集合或精确数值语义。

需要确定有符号与无符号溢出、显式环绕操作、除零、有符号最小值除以负一、移位范围、浮点行为以及比较与布尔运算规则。

**建议：**区分普通算术与显式环绕算术；固定有符号溢出语义。具体采用诊断、运行时陷阱或其他行为尚未决定。

### 7.3 显式转换

```text
c: u8 = cast<u8>a;
```

**待定：**整数缩窄和扩宽、符号变化、整数与浮点转换、枚举与整数转换、指针与整数转换、指针类型转换，以及非法转换和越界值的处理。

显式书写 `cast` 不表示任意类型之间都允许转换，也不表示转换必定采用截断语义。

### 7.4 地址、解引用与索引

**当前实现（2026-11-16）：**按用户要求支持一层整数指针 `*i32`、`&` 取普通整数变量地址、`*` 显式解引用读写、指针复制与参数/返回。null 为原生字面量，普通指针省略初始化时得到 null，不允许整数 0 隐式作为指针。直接可证明的空值解引用和直接返回本地对象地址有有限静态诊断；不增加动态检查或独立引用类型。已支持指针加减、i64 元素距离和 ==/!= 比较；编译期指针操作、多层指针、转换和排序尚未实现，详见[实现边界](pointer_subset_v0_1.md)。

**已确定的方向：**使用 `&` 获取地址、`*` 解引用，数组访问形式为 `arr[index]`。

**已确定（MEM-03）：**结构体成员访问必须在结构体对象表达式上使用 `.`；结构体指针先显式解引用，写作 `(*p).field`。不支持 `p.field`、自动指针追踪或 `p->field` 成员语法。`*p` 形成目标对象的访问表达式，不要求复制完整结构体。

```text
x: i32 = 10;
p: *i32 = &x;
buffer: [16]u8;
first: u8 = buffer[0];
```

依照已确定的默认零初始化规则，`buffer` 的元素均为 0，`first` 的值为 0。空指针、指针运算、索引类型、边界检查、对齐和存储有效性见第 10 节待定规则。

**已确定（ARRAY-01）：**当前数组采用目标 C 兼容的连续元素布局，编译器做有限静态越界检查，暂不生成运行时越界检查。可由常量与有限简单分析确定越界时给出编译错误；无法确定的动态索引允许编译，不要求先证明安全。静态检查通过不保证运行期访问合法，程序员仍须保证索引范围。

对元素类型表示兼容的正长度固定数组，存储为 N 个连续元素，大小为 N 乘以元素大小，对齐与元素一致，不附加隐藏长度/容量头部。零长度数组的大小/对齐已随 BD-16 接受，但不默认承诺其 C 兼容性；运行期长度、强类型数组的完整接口和值语义继续待审查。确认布局不自动接受 C 的所有数组退化和函数参数规则。

**后续探索：**动态边界检查、失败处置、可恢复接口和目标环境适配暂不作为当前实现要求。运行期非法越界不承诺被自动捕获，其精确非法行为分类仍由内存契约明确。详见审查稿 BD-15。

### 7.5 `sizeof` 与 `alignof`

**已确定：**提供语言内置操作 `sizeof`、`alignof`。

```text
bytes: u64 = sizeof(Vec2);
alignment: u64 = alignof(Vec2);
```

**当前首版建议：**在暂缓 `usize` 的 Windows x86-64 子集中，结果类型采用 `u64`。原草案的 `usize` 结果类型建议由 TYPE-03 继续追踪，以上代码是当前方案示例，尚未冻结。

**待定：**允许的操作数、求值阶段、是否求值表达式操作数，以及无完整布局类型的处理。

### 7.6 `match`

**已确定的方向：**提供 `match`，不设计传统 `switch`。

```text
result: i32 = match (value) {
    0 => 100,
    1 => 200,
    _ => 300,
};
```

**建议：**

- `match` 是表达式，也可以忽略结果作为语句使用。
- 不发生隐式 fallthrough，各分支拥有独立作用域。
- 对普通枚举与携带数据的枚举进行穷尽性检查。
- 普通整数原则上需要能够覆盖剩余值的分支。
- 初期模式包含常量、枚举变体与 `_`；复杂嵌套模式、守卫和范围模式后续扩展。
- 产生结果的分支满足一致的结果类型规则。

**待定：**被匹配值的求值次数、重复或重叠模式、不可达分支、分支结果定型、无结果分支与提前退出分支，以及变体解构的精确语法。

## 8. 语句与控制流

### 8.1 条件与循环

**已确定的方向：**

```text
if (condition) { ... } else { ... }
while (condition) { ... }
do { ... } while (condition);
for (init; condition; step) { ... }
loop { ... }

break;
continue;
return value;
```

`...` 在本例中为内容占位，不代表可直接编译的语法。

**已确定（2026-11-16）：**`if`、`while`、`do...while` 和 `for` 中显式出现的条件必须为 `bool`，指针、数值和其他类型不因处于条件位置而隐式转换为真假。指针没有特殊例外，普通 bool 赋值、参数与返回位置同样不隐式接收指针。

以下示例假设 `p` 是指向 bool 的指针；空值写法沿用当前 `null` 方案：

```text
if (p != null) { ... } // 合法：显式检查地址是否非空
if (*p) { ... }        // 条件类型合法：判断目标 bool；调用方须先保证 p 可解引用
if (p) { ... }         // 编译错误：条件不是 bool
if (!p) { ... }        // 编译错误：逻辑 ! 不接受指针
```

**决定理由：**保留统一的显式规则，减少条件上下文的特殊转换，并区分“地址非空”与“目标值为真”。非空判断不承诺地址有效、对齐正确或对象仍存活。未采用此前讨论的指针条件简写方案。

**已确定（BD-19，2026-11-16）：**

- `if/else` 和循环均为语句，循环不产生值。
- 保留 `while`、`loop`、`do...while` 和 `for (init; condition; step)`；for 省略条件等价于 true。
- 所有控制体必须使用 `{}`，单语句体和空体均不例外；换行、缩进及下一条裸语句不决定代码体归属。`else if` 保留为链式分支语法，各分支体仍必须使用 `{}`，独立 else 后必须为块。
- 无标签 break 退出最近的循环；首版不支持带标签 break/continue。
- while/do...while 的 continue 转到条件检查；for 的 continue 先执行 step 再检查条件；loop 的 continue 回到循环开头。
- return 退出当前函数；控制流退出经过相关作用域清理位置，defer 的执行顺序、求值等细节仍按第 8.2 节单独审查。

**待补齐：**完整无歧义 EBNF、for 初始化/迭代项的具体语法、不可达代码及返回路径分析。BD-20 仅已确认第 8.2 节列出的部分，BD-22 的其余规则继续待审查。

**Stage 0 实现记录（2026-11-16）：**本节 BD-19 已实现，包含 bool 值、整数比较、指针相等/不等、逻辑短路、if/else、全部上述循环及 break/continue。当前 for 初始化至多一条声明/赋值/调用，迭代项至多一条赋值/调用，均可省略；初始化作用域覆盖条件、迭代项及体。未提供逗号项、复合赋值或 ++/--。局部块允许内层遮蔽、同层重复报错，暂按 BD-12 候选；这些详细边界不自动冻结为长期标准。

当前保守检查可达末尾路径必须有返回，允许无出口的无限循环；只利用直接常量 bool 判断不可达，不证明任意算术或循环终止。不可达源码仍检查名称/类型，显式 := 常量仍必须求值成功。编译期函数也可执行分支/循环/终止递归，有资源预算，尚不支持编译期指针。完整实现文法与限制见[基础编译原型](parser_subset_v0_1.md)。defer 与 match 尚未实现。

### 8.2 `defer`

**已确定的方向：**提供 `defer`。

```text
defer {
    cleanup();
}
```

**已确定（2026-11-16）：**`defer` 在所属词法作用域退出时执行；同一作用域中已执行到的 defer 按登记的相反顺序执行。延迟体在实际执行时读取变量的当前值，不在执行 defer 语句时保存参数或变量快照。延迟体必须使用 `defer { ... }`，不提供单表达式体或默认绑定下一行语句的形式。

```text
n: i32 = 1;
defer {
    record(n);
}
n = 2;
// 作用域正常退出时 record 收到 2
```

**建议：**正常结束、return、break 和 continue 造成的作用域退出均执行相关清理；具体退出与清理边界按审查稿 BD-20 补齐。

**待定：**返回值与清理的先后、延迟体内允许的控制流、延迟体中允许的具体语句，以及硬件故障、非局部跳转和进程终止时的行为。语言已明确没有异常，不设计语言异常展开路径。

审查稿 BD-20 保留其他语言的设计对照；其作用域、逆序和退出时求值已接受，其余规则继续待审查。

## 9. 聚合类型与枚举

### 9.1 结构体

**已确定的方向：**`struct` 的字段同时存在。

```text
struct Vec2 {
    x: f32;
    y: f32;
}
```

**已确定（2026-11-16）：**支持 `{.field = expression}` 形式的指定字段初始化；允许省略部分字段，省略字段按其类型执行默认零初始化。

```text
struct Point {
    x: i32;
    y: i32;
}

value: i32 = 7;
p: Point = {.x = value};  // p.x 为 7，p.y 为 0
zero: Point;              // 两个字段均为 0
fixed: Point := {.y = 2}; // 常量聚合示意，x 为 0；当前原型尚未实现聚合
```

```text
invalid: Point = {.z = 1}; // 编译错误：Point 中不存在字段 z
```

**已确定（2026-11-16）：**同一结构体初始化器中，同一字段不得重复指定，即使两次初始化值相同也为编译错误；不采用后一次覆盖前一次的规则。

```text
duplicate: Point = {.x = 1, .x = 1}; // 编译错误：字段 x 重复初始化
```

以上示例中初始化器的类型来自目标声明。独立初始化表达式的类型确定、字段初始化项求值顺序、空初始化器、嵌套初始化器与位置初始化的规则仍待确定。

**已确定（BD-16，2026-11-16）：**首个 Windows x86-64 目标采用小端、自然对齐和声明顺序布局，各字段向上对齐，结构体对齐取字段最大对齐，总大小补齐到该对齐的倍数。不自动重排字段，首版不提供 packed、位域或自定义对齐。整数/浮点基本类型对齐为其 1/2/4/8 字节自然对齐，数据/函数指针对齐为 8。

空结构体大小为 **0 字节**、对齐为 **1 字节**。零长度数组大小为 0，对齐与元素相同；遵循自然布局计算后，仅包含零大小字段的结构体也可能大小为 0，其对齐仍由字段决定。以上零大小表示不默认声称兼容 C 结构体或其按值 ABI。

结构体和数组首版不提供自动 `==`，需要显式逐字段或库比较；不能以填充字节 memcmp 代替值比较。正大小普通 C 兼容成员的布局仍须与目标工具链及 ABI 对照，确认本条不等于完成完整 FFI 验收。

```text
struct Empty {}
marker: Empty;       // 有类型的零大小值，不需要为内容写入数据字节
// sizeof(Empty) 为 0，alignof(Empty) 为 1
```

**待定：**完整构造语法、字段访问表达式的可写性和临时对象边界、一般复制语义、C 兼容布局的声明方式，以及零大小对象的取地址、身份、分配和调用约定。零大小布局不自动确定其地址唯一性或原始指针算术规则，配套候选见审查稿 BD-16。

**已确定（MEM-03）：**`.` 统一负责结构体对象的字段定位；无论对象来自普通变量还是显式解引用，规则相同。指针本身不能直接用点号访问目标字段，必须写 `(*p).field`。此前允许点号直接接收一层指针的候选已撤回。例子与理由见审查稿 BD-13 的“结构体字段定位与显式解引用”。

### 9.2 无标签联合体

**已确定的方向：**`union` 的字段共享存储，不自动记录当前有效字段。

```text
union RawValue {
    integer: i32;
    floating: f32;
}
```

**待定：**大小与对齐、字段写入与读取的合法性、跨字段读取是否允许位重解释，以及别名规则。共享存储本身不确定这些行为。

### 9.3 普通枚举

**已确定的方向：**普通枚举表示离散值，支持显式指定整数底层类型。

```text
enum Color : u8 {
    Red,
    Green,
    Blue,
}
```

**待定：**默认底层类型、默认判别值、显式赋值语法、重复判别值、变体名称解析及非法整数值的处理。

### 9.4 携带数据的枚举

**已确定的方向：**支持由编译器维护标签和当前有效变体的判别联合体，并允许 `match` 解构。

```text
enum Expr {
    Integer(i64),
    Float(f64),
    Binary(*BinaryExpr),
}
```

**待定：**变体构造与解构、Payload 数量和命名、移动/复制、标签表示和内存布局。

**建议：**不默认承诺携带数据枚举符合 C ABI；需要 C 互操作时显式使用 C 兼容表示。

## 11. 模块与名称空间

本节整理当前讨论方案。模块限定访问使用 `::` 是用户已明确的方向；默认名、可选 `as`、`export` 与路径规则作为本轮工作草案记录，尚未整体冻结。早期的 `math.add` 模块访问和不支持别名的候选方案不再作为当前示例。

### 11.1 导入、别名与限定访问

`import` 引入模块并在当前模块绑定名称空间。模块文件的定位与导入方绑定的名字分别处理。

```text
// 默认模块名
import "math";

fn main() -> i32 {
    return math::add(1, 2);
}
```

```text
// 显式别名：同一个模块在当前文件中绑定为 m
import "math" as m;

fn main() -> i32 {
    return m::add(1, 2);
}
```

**当前方案：**

- `as` 可选；省略时以目标文件名去掉源文件扩展名后的部分作为默认模块名。
- 默认模块名不是合法标识符或与当前模块已有顶层名称冲突时，要求提供不冲突的显式别名。
- 模块中的公开声明通过 `math::add` 或 `m::add` 访问；对象字段使用 `.`，例如 `position.x`。
- 导入不自动把全部公开名称引入当前作用域。
- 首版导入声明位于模块顶层；局部导入、通配导入、选择性导入和再导出暂不纳入当前方案。

默认模块名和显式别名均可作为 `::` 左侧的限定名。模块限定访问本身不表示修改了模块名字，也不表示创建了新的模块实例。

### 11.2 公开声明

`export` 控制语言模块的公开接口。

```text
// math 模块
export fn add(a: i32, b: i32) -> i32 {
    return a + b;
}

fn helper(value: i32) -> i32 {
    return value;
}
```

**当前方案：**顶层声明默认模块私有；显式 `export` 的声明可被导入方通过限定名访问。上例的 `add` 可从其他模块访问，`helper` 保持模块私有。

语言模块的 `export` 不自动表示生成供 C 或其他外部程序使用的链接导出符号；后者由独立的 FFI/目标契约规定。

**待定：**可导出的声明种类、公开函数或类型引用私有类型时的规则、结构体字段可见性和未来再导出机制。

### 11.3 相对模块路径

**当前首版方案：**导入字符串相对于包含该 `import` 的源文件所在目录解析，并补上统一的源文件扩展名。首版示例省略扩展名，正式扩展名仍待决定。

```text
模块候选文件 = 导入方源文件目录 / 导入字符串 + 源文件扩展名
```

以下目录中的 `.my` 仅为扩展名占位示意，不是已确定的语言扩展名：

```text
project/
├── src/
│   ├── main.my
│   └── math.my
└── common/
    └── utils.my
```

`src/main.my` 中的导入示例：

```text
import "math";                     // project/src/math.my，绑定 math
import "../common/utils";          // project/common/utils.my，绑定 utils
import "../common/utils" as tools; // 同一个模块，另行绑定 tools
```

- 路径基准始终为导入方源文件目录，编译器进程的工作目录不参与该相对路径的含义。
- 导入字符串中的 `/` 用作目录分隔符，允许通过 `.`、`..` 表达相对路径。
- 文件不存在时给出编译错误，诊断显示导入位置与实际尝试的完整路径。
- 当前方案仅定义相对源文件导入；绝对路径、显式扩展名、目录入口文件、标准库前缀、包名和额外搜索目录的规则尚未确定。
- 将来若支持标准库或第三方包，应显式扩展解析规则，不能让当前已合法的相对导入悄然绑定到其他模块。

### 11.4 模块身份与依赖

**建议：**

- `import` 是模块解析和名称空间绑定，不进行源码文本粘贴。
- 一次编译中，同一个规范化模块身份只加载并解析一次；别名是导入方的名称绑定，不改变模块身份。
- 同一个模块可以用不同名字绑定；重复声明同一绑定名的处理仍需确定。
- 模块先提供顶层声明，再按需解析与检查内容，保持顶层声明顺序无关。
- 循环导入不必一律禁止，但不可解的编译期依赖循环必须诊断。
- 编译期生成的新导入和受影响声明继续参与模块处理；AST 变更可以触发重新分析。

**待定：**Windows 路径大小写、路径规范化、符号链接/文件别名如何影响模块身份，名称遮蔽与重复绑定，循环模块初始化及编译期生成导入的路径基准。首个实现应在相关代码落地前明确这些边界。

## 12. 编译期执行与 AST 元编程

### 12.1 能力边界

**已确定的方向：**

- `run` 支持表达式求值和代码块执行。
- 编译期执行能够表达普通语言计算，不仅限于常量折叠。
- 编译期程序能够访问、构造和修改任意 AST，包括生成声明。

```text
fn square(x: i32) -> i32 {
    return x * x;
}

n: i32 := run square(8);

run {
    // 执行编译期代码，通过 AST API 查询、生成和修改程序
}
```

“任意 AST 修改”是语言能力目标，不表示允许破坏编译器内部不变量；也不表示可不经诊断地修改任意正在执行的代码。

### 12.2 编译期与运行期一致性

原草案要求对编译期与运行期的相同运算验证语义一致性。具体运算规则必须在核心语言语义中统一确定，不能分别由解释器和后端自行决定。

目标相关值（如布局和指针宽度）、运行期地址以及外部函数在编译期的可用性需要单独规定，不能从“普通计算”推出编译期允许所有运行期操作。

### 12.3 建议的修改约束

**建议：**

- 执行前完成必要的名称解析和类型检查。
- AST 读写经过受控 API，并登记变更。
- 受影响的符号、类型和依赖结果失效，随后重新分析。
- 新生成的声明、导入和 `run` 进入发现与分析流程。
- 最终代码生成基于语义稳定的程序。
- 对不可解的依赖循环给出诊断，并提供终止无限执行或资源耗尽编译的机制。

采用解释器是编译器的推荐实现方式，不是要求所有兼容实现都必须采用的语言规则。

### 12.4 必须讨论的开放问题

- 多个 `run` 的执行顺序，含跨模块顺序。
- `run` 表达式与顶层代码块的调度、重复求值和结果缓存。
- 正在分析或执行的 AST 被修改时，修改何时生效。
- 已执行的 `run` 被修改或依赖失效后是否重新执行，以及副作用如何处理。
- 新声明与原声明冲突，以及删除、重命名和替换声明的规则。
- AST 节点身份、类型值、作用域、源码位置和 API 的公开表示。
- 文件、系统调用和其他外部副作用的可用范围。
- 编译期地址或对象如何转成运行期产物。
- 依赖循环、资源限制及可复现构建的边界。

本节是后续独立 Comptime 规范的起点；拆分前以本文为唯一语言规则来源，避免多份文档重复定义。

## 13. C 互操作与执行环境

### 13.1 外部函数

**已确定的方向：**以完整目标平台 C ABI 兼容为正式目标，属性示例如下。

```text
[[extern(C)]] fn puts(text: *u8) -> i32;
```

该示例只表达外部 C 函数声明意图；`*u8` 的可写性和字符串规则尚未确定，不应据此推断完整的 C 类型映射。

C ABI 兼容不表示编译器必须解析 C 源码或 C 头文件。

### 13.2 首次实现的边界

**建议：**首版优先覆盖自举所用的 ABI 子集，完整兼容另行验收。子集应列出支持的参数类型、返回值类型、导出、回调和可变参数范围。

具体的寄存器、栈布局、shadow space、聚合传递和栈展开等属于目标 ABI 实现契约。语言规范负责说明哪些声明允许跨边界，以及这些声明具有什么类型和行为。

**待定：**默认语言调用约定、外部符号名称、C 类型映射、C 兼容聚合布局、函数指针兼容性、可变参数和程序入口。

初期错误处理建议使用普通返回值或错误码；不要求先实现专门的 Result 语法。语言不提供异常机制已确定。

## 14. 诊断与规范验证

本节为从原草案测试目标整理出的验证建议，不表示所有诊断类别已定义。

每条冻结规则应尽量具备：

1. 合法程序及其类型或可观察结果。
2. 非法程序及预期诊断类别。
3. 必要的边界用例。
4. 若可在两个阶段执行，编译期与运行期的一致性用例。

错误信息应关联源码位置。具体文案不必成为语言兼容性要求。

涉及非法程序或运行时错误的测试，应先根据已确定规则分类；不能把当前编译器恰好出现的行为直接当作规范。

首次自举还需通过多阶段构建、编译器回归、优化前后行为一致性和 C ABI 双向测试；这些工程验收要求见架构文档第 5 节。

## 附录 A. 核心可自举子集候选（新增讨论建议，非规范性）

本附录用于开始讨论，不是原草案已经确认的范围变更。完整语言目标继续保留；是否调整原 M2 先于 M4 的验收依赖，需要明确决定。

### A.1 范围判断方法

以“能够编写和构建编译器自身”为依据，先列出编译器实际需要表达的对象和操作：

- 源码字节、Token、源码位置和错误信息。
- AST、符号、类型、IR 指令及控制流图。
- 动态数组、字符串缓冲、映射及内存分配。
- 多文件源码组织、文件读取、汇编输出和进程退出。

这些需求可以有多种语言表达方式。自举不必先实现全部语法糖，但不能把缺少的表达能力转移成隐含且未规定的特殊行为。

### A.2 建议的首轮范围

| 范围 | 建议纳入的能力 | 原因或取舍 |
| --- | --- | --- |
| 基础计算 | `bool`、固定宽度整数、字面量、显式转换；`usize/isize` 是否纳入见 TYPE-03 | 词法、索引、大小和地址相关计算 |
| 函数与存储 | 函数、递归、局部绑定、所需全局存储、显式返回 | 表达编译器算法；初始化规则需先确定 |
| 数据结构 | 指针、结构体、定长数组、字段访问、索引 | 表达 AST、符号表、IR 和缓冲区 |
| 控制流 | `if/else`、`while` 或 `loop`、`break/continue` | 足以表达首轮算法，具体保留哪种循环待讨论 |
| 工程组织 | 模块导入和明确的名称解析 | 支持可维护的多文件编译器 |
| 执行环境 | 自举所需 C ABI、分配/释放、文件 I/O、输出、退出 | 可通过固定签名的 C 封装缩小首轮 ABI 范围 |
| 编译期基础 | 按需纳入最小 `run`、常量/类型查询 | 是否为首次自举必备，取决于编译器源码是否使用 |

固定签名 C 封装是一种候选基础库方案，若采用，应明确它属于保留的外部依赖。

### A.3 需要选择的取舍

| 能力 | 首次自举中的价值 | 可选路径 |
| --- | --- | --- |
| 普通枚举 | 表达 Token 与节点类别 | 尽早支持，或临时使用具名整数常量 |
| Payload 枚举与 `match` | 简化 AST/IR 的表达和分派 | 直接纳入，或先采用标签与结构体/联合体 |
| `union` | 紧凑表示变体数据和底层互操作 | 按真实布局需求纳入；不能仅因保留了语法就认为自举必需 |
| `defer` | 简化资源清理和错误路径 | 尽早支持，或先显式清理 |
| 函数指针 | 回调、可替换策略与 ABI 互操作 | 取决于首版编译器和 C 接口是否需要 |
| `f32/f64` | 编译用户语言中的浮点程序 | 编译器可用整数表示浮点位模式；完整支持时机待定 |
| 完整 `run` 与任意 AST 修改 | 实现语言的重要长期能力 | 可按原路线在首次自举前完成，或先完成独立的基础自举 |

“实现编译期解释器”和“编译器自身使用编译期元编程”是两件事。前者可以用普通运行期代码实现；后者会增加 Stage 0 必须支持的能力。

是否将完整 Comptime 验收与首次自举拆开，是 CORE-01 的核心问题，本文不代为决定。

## 附录 C. 核心子集确认流程（讨论建议，非规范性）

建议先明确足以约束首个编译闭环的规则，再实现该闭环，不等待全部长期能力冻结。

| 顺序 | 确认内容 | 可检查的产物 |
| --- | --- | --- |
| 1 | 子集边界与代表性程序 | 入口、函数调用、结构体/指针、缓冲区、多文件调用及 C 接口的小程序草图 |
| 2 | 类型、字面量和绑定 | 类型清单、默认/上下文定型、显式转换、初始化及可变性规则 |
| 3 | 表达式和数值行为 | 运算符表、求值顺序、短路、溢出与非法运算规则 |
| 4 | 内存与聚合 | 布局、复制、指针/索引、生命周期及非法访问规则 |
| 5 | 控制流、模块和执行环境 | 返回、循环、清理、`import/export`、入口及首轮 C ABI 契约 |
| 6 | 词法与语法收敛 | 前述功能所需的完整词法和 EBNF，消除解析歧义 |
| 7 | 冻结首个端到端子集并实现 | 为已冻结规则准备正例、反例及预期结果，贯通解析到可运行产物 |
| 8 | 扩展至可自举子集 | 按真实需求加入更多聚合、基础库与 Comptime，并逐项补齐契约 |

上述顺序允许交叉讨论；词法和语法在设计过程中同步记录，在 Parser 实现前补齐。若 CORE-01 决定首次自举必须具备完整 AST 元编程，应提前确定其关键调度与修改边界。

每轮讨论应区分“用户已明确接受的规则”和“仍在评估的建议”；只有前者进入已确定规则。实现不能依靠未记录的临时语义填补空缺。
